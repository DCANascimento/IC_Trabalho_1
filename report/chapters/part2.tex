Moving to the codecs, the \textbf{\textit{Lossless Audio Codec}} is a program that takes an audio file and compresses it, to as small of a size as possible, while making all the information in the original recoverable through decompression.

\section{Our Implementation}

This part of the work was split into a few submodules:

\begin{itemize}
    \item \textbf{wav.cpp} allows us to read/write a wav file. From a wav file, besides the PCM audio samples that are later encoded, we also take metadata, such as sample rate, number of channels, bits per sample and audio format. During decoding, this data is written back in, alongside the original audio samples.
    
    \item \textbf{predictor.cpp} takes the raw vector and through residual calculation it reduces the space required to store the data. (Write specifics?)
     
    \item \textbf{zigzag.cpp} applies the zigzag method to convert signed integers into unsigned integers, and vice versa. This simply serves to enable rice encoding later on, as it only takes in positive integers.
    
    \item \textbf{rice.cpp} takes the values transformed by the zigzag, and converts them to bits, and vice versa. For this encoding method, a difficulty that arised was the decision of the \textbf{k} variable. This variable is what decides the length of the bit representation of each samples. However, there is no single value of \textbf{k} that always garantees the shortest possible encoding, and sometimes even the best value ends up longer than the original PCM stream. Given this, our code has a range of \textbf{k} values that are tested and compared (including the original samples), and the most efficient compresion variable is kept and used.

    \item \textbf{bitstream.cpp} takes the values transformed by the zigzag, and converts them to bits. Besides the compressed sample values, it also converts and stores important data for decoding, like the \textbf{k} variable obtained in the rice method, 
\end{itemize}

\section{Final Adjustments}

Given our obtained results, we decided on some changes that could potentially improve our compression results:

\begin{enumerate}

    \item \textbf{MID/SIDE channels:} By taking the difference between the left and right channels (assuming stereo), as well as the average of the two, we can potentially obtain smaller values to the original ones, increasing compression rate. However, like with Rice encoding, if the resulting values are larger, we can choose to keep the originals.
    
    \item \textbf{Predictor adjustment:} By using a second order predictor, as opposed to first order, we can model smooth waveforms by tracking signal trends and slopes rather than assuming a flat line, resulting in significantly smaller residuals and improved compression efficiency
        
    \item \textbf{Block encoding:} Before, we would apply the whole enconding strategy to the entire sample field, all with the same parameters. Now, we have decided to split the samples into blocks, and each block now has its own compression parameters. So each block can either have L/R or MID/SIDE transformation, choose between first or second order predictor, define a favorable k variable for rice encoding, and decide whether to do said encoding or keep the raw PCM samples (for all of these, each block is tested at runtime and the best result is chosen)

\end{enumerate}
